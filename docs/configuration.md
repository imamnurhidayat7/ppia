# Configuration

All backend configuration is environment-driven. Copy `api/.env.example` to
`api/.env` and fill in real values — `.env` is gitignored and must never be
committed.

## API environment variables

### Server

| Variable | Default | Description |
| --- | --- | --- |
| `PORT` | `4000` | Port the API listens on. |
| `API_URL` | `http://localhost:4000` | Public base URL of the API, used to build absolute links in e-mails. |
| `FRONTEND_URL` | `http://localhost:3000` | Origin of the web app. Always allowed by CORS and used in e-mail links. |

### Database

| Variable | Description |
| --- | --- |
| `DATA_SOURCE` | `local` or `supabase`. Selects the database *and* the storage driver together. When unset it is inferred from whichever connection variables are present. |
| `LOCAL_DATABASE_URL` | Connection used when `DATA_SOURCE=local`. Defaults to `postgresql://postgres:postgres@localhost:5432/ppia?schema=public`. |
| `SUPABASE_DATABASE_URL` | Runtime connection used when `DATA_SOURCE=supabase`. The pooled (6543) URL is fine here. |
| `SUPABASE_DIRECT_URL` | Direct (5432) connection for Prisma migrations. DDL cannot run through the transaction pooler, so this is required whenever the runtime URL is pooled. |
| `DATABASE_URL` | Fallback connection, used when the variable for the selected source is missing. With `DATA_SOURCE` unset it also decides the source (a `supabase.` host means `supabase`), which is what lets a host that injects it (Render, Fly, Heroku) work unchanged. Note it does **not** override an explicit `DATA_SOURCE`: with `DATA_SOURCE=local`, `LOCAL_DATABASE_URL` wins. |
| `DIRECT_URL` | Manual override for the migration connection. |

The resolver lives in `api/src/lib/data-source.ts` and writes the values it picks
back into the environment, because Prisma reads `env("DATABASE_URL")` from the
schema. The `db:*` npm scripts run the Prisma CLI through it, so migrations
always target the selected database.

### File storage

| Variable | Default | Description |
| --- | --- | --- |
| `STORAGE_DRIVER` | inferred | `local` writes uploads to disk; `supabase` writes to Supabase Storage. When unset it resolves to `supabase` if `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are both present, otherwise `local`. Always wins over the `DATA_SOURCE` inference, so `DATA_SOURCE=supabase` + `STORAGE_DRIVER=local` is how files live on a Hostinger VPS while the database stays on Supabase. |
| `STORAGE_LOCAL_DIR` | process working directory | Base directory for the local driver. Public files go to `<base>/uploads`, private documents to `<base>/storage/private`. On a VPS point this at a persistent path (it must survive redeploys). |
| `PUBLIC_FILES_BASE_URL` | driver default | Public base URL under which stored object KEYS resolve to browser URLs: `${API_URL}/uploads` for the local driver, `<SUPABASE_URL>/storage/v1/object/public/<bucket>` for Supabase. Set explicitly when files are served from anywhere else (CDN, custom domain). Must match the web's `NEXT_PUBLIC_FILES_BASE_URL`. Logged at API boot (`Public files base: …`) — check that line after every deploy. |
| `LEGACY_PUBLIC_BASES` | *(empty)* | Comma-separated historical base URLs, used only by the one-off `npm run storage:normalize-keys` script (e.g. `http://localhost:4000/uploads`, a retired domain) so old absolute URLs collapse to keys. |

Database rows keep the stable object KEY (`1720000000-123.png`), never the
absolute URL — new uploads persist `key` from the upload response. Readers
resolve keys at display time, so moving file storage is an env change plus a
file copy, never a code edit. Absolute legacy URLs and pasted external URLs
pass through untouched.

Under the local driver, private documents are served only through
`GET /api/private-files/...` with an HMAC-signed, expiring link generated by the
admin-only document endpoint. They are never placed inside the publicly served
`uploads` directory.

### Authentication

| Variable | Description |
| --- | --- |
| `JWT_SECRET` | Signing secret for JSON Web Tokens. Use a long, random, per-environment string. Rotating it invalidates every issued token. **Required.** |

### E-mail (Mailtrap)

Transactional mail is sent through the Mailtrap HTTP API (`api/src/lib/mailer.ts`).
If `MAILTRAP_TOKEN` is empty, the API logs e-mails to the console instead of sending
them, so local development works without credentials.

| Variable | Default | Description |
| --- | --- | --- |
| `MAILTRAP_USE_SANDBOX` | `true` | When `true`, nothing reaches real recipients; every message lands in the Mailtrap inbox named by `MAILTRAP_INBOX_ID`. Set to `false` only once the sending domain is verified. |
| `MAILTRAP_TOKEN` | *(empty)* | API token for Mailtrap sending. `MAILTRAP_API_KEY` is accepted as an alias. |
| `MAILTRAP_INBOX_ID` | *(empty)* | Required only when `MAILTRAP_USE_SANDBOX=true`. |
| `MAIL_FROM` | `no-reply@ppiaauckland.org` | Envelope sender. In production the domain must be verified in Mailtrap. |
| `MAIL_FROM_NAME` | `PPIA Auckland` | Display name on outbound e-mail. |

### Rate limiting

| Variable | Default | Description |
| --- | --- | --- |
| `TRUST_PROXY` | *(unset)* | Number of reverse proxies in front of the process (`1` behind a single nginx/load balancer), or a comma-separated list of addresses. Required for correct client IPs behind a proxy. Leave unset when reached directly — trusting `X-Forwarded-For` without a proxy lets callers spoof their address and bypass the limiter. |
| `RATE_LIMIT_DISABLED` | `false` | Set to `true` to switch off rate limiting. Local development only. |

### CORS

| Variable | Description |
| --- | --- |
| `CORS_ORIGINS` | Extra browser origins allowed to call the API, comma-separated (staging host, custom domain). `FRONTEND_URL` is always allowed, and `localhost:3000` / `localhost:3001` are always allowed for local development. |

## Web environment variables

The web app reads public variables at build time. They must be prefixed with
`NEXT_PUBLIC_` to be exposed to the browser.

`web/.env.local`:

| Variable | Default | Description |
| --- | --- | --- |
| `NEXT_PUBLIC_API_URL` | `http://localhost:4000` | Base URL of the API the browser client calls. |
| `NEXT_PUBLIC_FILES_BASE_URL` | `${NEXT_PUBLIC_API_URL}/uploads` | Public base URL that stored file keys resolve against. Must mirror the API's `PUBLIC_FILES_BASE_URL`. Deployments whose files live outside the API (Supabase Storage, CDN) must set this explicitly — otherwise direct-loaded images break while optimizer-loaded copies keep working. Build-time: changing it requires a rebuild. |
| `NEXT_PUBLIC_IMAGE_HOSTS` | *(empty)* | Comma-separated extra image origins (previous storage host during a migration transition, CDN). Added to the CSP `img-src` and the image-optimizer allowlist. |

Moving files between hosts is config-only: keep the two files-base variables
identical, copy objects with the same keys, and run the normalisation script.
Full steps in [Deployment → Moving file storage without code
changes](deployment.md#moving-file-storage-without-code-changes).

## Notes on secrets

- `JWT_SECRET` and `DATABASE_URL` are the two values that must always be set and kept
  private.
- Use distinct `JWT_SECRET` values per environment (dev / staging / production).
- Do not commit `.env` or `.env.local`. Only `.env.example` (placeholders) is tracked.
